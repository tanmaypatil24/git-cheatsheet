# 29. Conventional Commits: Standardization

In professional team environments, messy commit histories (like `fixed it`, `bug fixes`, `changes`) make it impossible to audit updates, debug breaks, or automate releases. **Conventional Commits** is a lightweight specification that adds a clean, human-readable, and machine-parsable structure to commit messages.

---

## The Conventional Commit Structure

A conventional commit message is structured as follows:

```text
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

### Explaining the Blocks:
1. **Type (Mandatory)**: A short prefix specifying the intent of the commit (e.g. `feat`, `fix`).
2. **Scope (Optional)**: A contextual noun indicating what part of the application was modified (e.g., `auth`, `billing`). Wrapped in parentheses.
3. **Description (Mandatory)**: A short, imperative-mood summary of the changes (lowercase, no period at the end).
4. **Body (Optional)**: A detailed explanation of what was changed and why. Separated from the description by a blank line.
5. **Footer (Optional)**: Used to reference tracking tickets (e.g. `Closes #142`) or highlight breaking changes.

---

## Core Commit Types

Here are the standard commit prefixes adopted across modern software development:

| Type | Name | Purpose | SemVer Impact |
| :--- | :--- | :--- | :--- |
| **`feat`** | Feature | Introduces a new feature to the codebase. | **`MINOR`** |
| **`fix`** | Bug Fix | Corrects a bug or issue in the application. | **`PATCH`** |
| **`docs`** | Documentation | Edits markdown files, comments, or documentation. | *None* |
| **`style`** | Code Style | Modifies formatting, spacing, semicolons (no code logic changes). | *None* |
| **`refactor`**| Code Refactoring| Modifies code logic without changing external behavior or fixing bugs.| *None* |
| **`test`** | Testing | Adds, corrects, or updates unit or integration tests. | *None* |
| **`chore`** | Maintenance | Updates build scripts, dependencies, configs (no source code edits).| *None* |

## Documenting Breaking Changes

A **Breaking Change** indicates that a commit introduces modifications that are incompatible with previous versions of your software, requiring a **`MAJOR`** SemVer release bump.

You represent a breaking change in two ways:
1. Append an exclamation mark (`!`) immediately after the type or scope prefix.
2. Add a `BREAKING CHANGE:` footer block explaining the change.

##### Real-world Examples:
```text
# Example 1 (Exclamation mark syntax)
refactor(api)!: remove support for XML endpoints

# Example 2 (Footer syntax)
feat(checkout): support new Stripe API version

BREAKING CHANGE: The old Stripe configuration client keys are no longer supported.
```

## Real-world Commit Message Examples

### 1. Simple Feature Commit
```text
feat(auth): add google oauth2 login support
```

### 2. Bug Fix with Ticket Closing
```text
fix(payment): resolve crash on Stripe checkout when cart is empty

Closes #104
```

### 3. Detailed Refactoring Commit
```text
refactor(performance): optimize user image loading query

- Rewrote SQL query to include sub-joins
- Cached responses using Redis with a 10-minute TTL
- Added unit tests for empty image databases
```

## Why Adopt Conventional Commits?

- **Autogenerated Changelogs**: Automated release utilities (like `semantic-release` or standard changelog packages) can parse your commit logs and instantly generate beautiful `CHANGELOG.md` files for your project release.
- **Automated SemVer Bumps**: Automated workflows parse the commit types (`feat` -> minor, `fix` -> patch, `BREAKING CHANGE` -> major) to automatically calculate the next SemVer release number.
- **Better Code Reviews**: Reviewers instantly understand what a developer's code commits accomplish simply by scanning the git log.

---

## Best Practices
- **Use imperative mood**: Write the description as if you are giving a command to the codebase: `add Google login` instead of `added Google login` or `adds Google login`.
- **Keep descriptions short**: The description line should remain under **50 characters** to ensure beautiful scannability in terminals and GitHub logs.
- **Enforce with Commitlint**: Use Commitlint as a git hook (pre-commit/commit-msg) to verify that no team member can commit disorganized, messy messages.
